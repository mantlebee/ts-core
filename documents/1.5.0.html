    1.5.0 — upgrading from 1.4.0

    Version 1.5.0 adds the JsonValue and IsoDateTime types with their runtime checks, documents escapeHtml precisely, ships separate type declarations for ES module consumers and compiles to ES2020 instead of ES6. There are no changes to existing APIs: code that compiles and runs against 1.4.0 compiles and runs against 1.5.0 in every environment listed in section 4.

    1. JSON values

    JsonValue is the type of a value that survives a JSON.stringify / JSON.parse round trip unchanged; isJsonValue checks it at runtime and narrows unknown. The check is recursive and strict: it rejects whatever JSON.stringify would drop, change or fail on, at any depth.

    API 1.4.0 1.5.0
    JsonValue — string | number | boolean | null | JsonValue[] | { readonly [key: string]: JsonValue }
    isJsonValue — (value: unknown) => value is JsonValue
    Value isJsonValue
    strings, finite numbers (-0 included), booleans, null true
    lists and plain objects ({}, Object.create(null)) of JSON values true
    the same object referenced twice, without a cycle true
    undefined, also as a property value, a list item or a hole of a sparse list false
    functions, symbols, bigints false
    NaN, Infinity, -Infinity false
    Date, class instances, Map, Set, RegExp, boxed primitives false
    cyclic structures false

    The list member is JsonValue[], the same type as List<JsonValue>: a type alias cannot reference itself through another generic alias (TS2456).

    import { isJsonValue, JsonValue } from "@mantlebee/ts-core";

    function save(key: string, value: unknown): void {
      if (!isJsonValue(value)) throw new TypeError(`${key} is not serializable`);
      const json: JsonValue = value; // narrowed
      localStorage.setItem(key, JSON.stringify(json));
    }

    isJsonValue({ a: [1, "x", null] }); // true
    isJsonValue({ at: new Date() });    // false: serialize the date first
    isJsonValue({ a: undefined });      // false: JSON.stringify would drop "a"

    2. ISO 8601 date times

    IsoDateTime names the string format of dates exchanged as JSON: YYYY-MM-DDTHH:mm:ss.sssZ in UTC, with optional milliseconds, the output of Date.prototype.toISOString and of createHttpGetQuery for dates. isIsoDateTime checks both the shape and the calendar. Since IsoDateTime is a plain string alias, the check returns boolean and does not narrow.

    API 1.4.0 1.5.0
    IsoDateTime — string
    isIsoDateTime — (value: string) => boolean
    Input isIsoDateTime
    2026-01-01T00:00:00.000Z, 2026-01-01T00:00:00Z true
    2024-02-29T12:00:00Z (leap year) true
    2023-02-29T12:00:00Z, 1900-02-29T12:00:00Z false
    2026-04-31T00:00:00Z, 2026-13-01T00:00:00Z false
    2026-01-01T24:00:00Z, 2026-12-31T23:59:60Z false
    2026-01-01T00:00:00+00:00, …+01:00 false
    2026-01-01T00:00:00 (no Z), …z, … (space for T) false
    …00.1Z, …00.1234Z (milliseconds not 3 digits) false
    +002026-01-01T00:00:00.000Z (expanded year) false

    24:00:00 is valid ISO 8601 but rejected, as are leap seconds, because neither is what toISOString produces. An offset of +00:00 denotes the same instant as Z but is rejected: the type promises one canonical form, so values can be compared and sorted as strings.

    import { IsoDateTime, isIsoDateTime } from "@mantlebee/ts-core";

    interface Order {
      id: string;
      createdAt: IsoDateTime;
    }

    isIsoDateTime(new Date().toISOString()); // true
    isIsoDateTime("2026-01-01T10:00:00+01:00"); // false: convert to UTC first

    3. escapeHtml

    escapeHtml has been available since 1.0.0; its behaviour is unchanged. Its parameter is renamed from str to value (a rename of a positional parameter does not affect callers) and its documentation now states that every char other than & < > " ' is left untouched, so text without those five chars comes back unchanged. It is not idempotent on text that already contains entities: &amp; becomes &amp;amp;.

    import { escapeHtml } from "@mantlebee/ts-core";

    escapeHtml(`<a title="x">Tom & 'Jerry'</a>`);
    // "&lt;a title=&quot;x&quot;&gt;Tom &amp; &#39;Jerry&#39;&lt;/a&gt;"
    escapeHtml("àèì 😀"); // "àèì 😀"

    4. Packaging: ESM declarations and the ES2020 target

    ESM declarations

    The package has no "type": "module", so its .d.ts files are CommonJS declarations for TypeScript. Up to 1.4.0 exports["."] had a single types condition, shared by import and require: with moduleResolution node16 / nodenext, an ES module importing the package got CommonJS declarations for an ES module file ("masquerading as CJS" in arethetypeswrong). The build now runs scripts/emit-esm-types.mjs after tsc-alias, which copies every dist/src/**/*.d.ts to dist/esm/**/*.d.mts adding the .mjs extensions that ES modules require, and each condition points at its own declarations:

    "exports": {
      ".": {
        "import": {
          "types": "./dist/esm/index.d.mts",
          "default": "./dist/esm/index.mjs"
        },
        "require": {
          "types": "./dist/src/index.d.ts",
          "default": "./dist/index.js"
        }
      }
    }

    The top-level main, module and types fields are unchanged, for tools that don't read exports. With moduleResolution: "bundler" (Vite, esbuild) TypeScript picks the import condition, so it now reads the .d.mts, which declare the same API.

    ES2020 target

    The JavaScript is compiled to ES2020 instead of ES6. Optional chaining, nullish coalescing, async / await, exponentiation and object spread are emitted as written instead of being rewritten into helpers: no more __awaiter / __generator state machines, so the output is smaller, debuggable and its stack traces follow the source; the tslib helpers inlined into dist/esm/vendor are gone. Class fields are still compiled as before (they are ES2022), so their semantics are unchanged.

    Minimum environment: browsers released since 2020 (Chrome / Edge 80, Firefox 74, Safari 13.1) and Node.js 14 or later.

    This is not a breaking change because the actual minimum was already ES2020: 1.4.0 used globalThis (ES2020) at runtime, AbortableDelegate and the HTTP requestors depend on AbortController (Safari 12.1, Node 15), the response readers on WritableStream, and nothing in 1.x ran on Internet Explorer or on the Node versions ES6 output was still meant for (Node 12 reached end of life in April 2022). The change of syntax narrows no environment the library worked in. The one setup to check is a toolchain whose parser predates ES2020 and that parses node_modules without transpiling them (webpack 4, whose acorn 6 rejects ?.): transpile @mantlebee/ts-core with Babel or upgrade to webpack 5. Vite, esbuild, Rollup, webpack 5, Jest and Node.js parse ES2020 natively.

    Item 1.4.0 1.5.0
    exports["."] types one types for both import.types → .d.mts, require.types → .d.ts
    ESM declarations — dist/esm/**/*.d.mts
    build script … && tsc-alias … && tsc-alias && node scripts/emit-esm-types.mjs
    Compilation target ES6 ES2020
    dist/esm/vendor (tslib) inlined helpers removed, no helpers needed

    5. Checklist

    1. Update the dependency: npm install @mantlebee/ts-core@^1.5.0.
    2. If you compile with moduleResolution node16 / nodenext and had workarounds for the CommonJS declarations of the ESM entry (a // @ts-ignore, a paths override, skipLibCheck only for this package), remove them.
    3. If you run on a browser older than 2020 or on Node.js 12, or bundle with webpack 4 without transpiling node_modules, transpile the package or stay on 1.4.0 (but see section 4: AbortableDelegate and the HTTP requestors already required newer environments).
    4. Replace local copies of a JSON value type, a JSON check or an ISO date-time regex with JsonValue, isJsonValue, IsoDateTime and isIsoDateTime where they match the semantics in sections 1 and 2.
