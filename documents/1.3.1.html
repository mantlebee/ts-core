    1.3.1 — upgrading from 1.3.0

    Version 1.3.1 is a bug fix release: AbortableDelegate no longer relies on object identity to tell whether a call is still the latest one, so it works when the instance is read through a proxy. There are no breaking changes and no API changes: existing code keeps compiling and behaving the same.

    • 1. AbortableDelegate through a proxy
    • 2. Checklist

    1. AbortableDelegate through a proxy

    When the function of a call settled, AbortableDelegate decided whether that call was still the latest one by comparing the object it had stored for the call with the one read back from this, by identity (===). The comparison holds on a plain instance, but not on an instance read through a membrane proxy: a Proxy whose get trap wraps the objects it returns in proxies of their own, as reactive and observable libraries do. There the object read back from this is a proxy of the stored one, never identical to it, so the call never settled: its promise stayed pending, isRunning stayed true and the next call() rejected at once with AbortedException, while the side effects of the function still happened.

    The class now identifies each call with a sequence number, a primitive that no proxy can substitute, and compares that. The AbortController of the running call is no longer stored in the instance either: abort() reaches it through a closure, because a platform object cannot be operated through a proxy and a membrane that wraps every object would hand one back. The behaviour on a plain instance is unchanged.

    API 1.3.0 1.3.1
    AbortableDelegate.call() never settles when the instance is read through a membrane proxy settles the same way inside and outside a proxy

    The alternative was to leave the code as it was and document that the instances of the package must not be wrapped in such proxies. The change was preferred because it costs nothing, removes a dependency on object identity that the semantics of the class never needed ("is this call the latest one" is a question about order, which a sequence number answers directly), and spares every consumer a constraint that is invisible until a read hangs.

    The other classes that keep state in the instance were checked for the same defect; none has it. AsyncLock uses its queue only to dequeue, never to compare; DebouncedDelegate compares its timer handle with null only; ListItemDisposable and EventBus compare by identity, but synchronously and with values the caller supplied, never with a value read back from this after an await.

    2. Checklist

    1. Update the dependency: npm install @mantlebee/ts-core@^1.3.1.
    2. If you unwrapped an AbortableDelegate before calling it (e.g. with a toRaw-like helper) only to work around the hang, the unwrapping is no longer needed; keeping it is harmless.
