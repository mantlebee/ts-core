# 1.3.0 — upgrading from 1.2.1

Version 1.3.0 adds two primitives for async calls that overlap:
`AbortableDelegate` ("the latest call wins") and `AsyncLock` ("one call at a
time on a shared resource"). There are no breaking changes and no changes to
existing APIs: existing code keeps compiling and behaving the same.

- [2. AsyncLock](#2-asynclock)

## 1. AbortableDelegate

Running the same async function repeatedly (a search as the user types, a
reload while a filtered read is in flight) needs a rule for the calls that
overlap. Without one, the state ends up with the result of the call that
**resolves** last instead of the one **requested** last, and a "loading" flag
goes off when the first call ends while the second is still running.

`AbortableDelegate` wraps an async function so that **the latest call wins**.
It sits next to `DebouncedDelegate` in `delegates/` and uses the standard
`AbortController` / `AbortSignal`, already used by `HttpAbortController`.
Browsers and Node ≥ 17.3 support everything described below; on Node 15 to
17.2 the class works, but `signal.reason` is `undefined` and
`signal.throwIfAborted()` does not exist.

| API                                      | 1.2.1 | 1.3.0                                                                                                                       |
| ---------------------------------------- | ----- | --------------------------------------------------------------------------------------------------------------------------- |
| `AbortableDelegate<TArgs, TResult>`      | —     | runs `(signal, ...args) => Promise<TResult>`; a new `call()` aborts the running one                                         |
| `AbortableDelegate.call(...args)`        | —     | resolves with the result of this call; rejects with `AbortedException` when superseded or aborted                           |
| `AbortableDelegate.abort()`              | —     | aborts the running call, if any; no-op otherwise                                                                            |
| `AbortableDelegate.isRunning`            | —     | `true` from a `call()` until the **latest** call settles                                                                    |
| `IAbortableDelegate<TArgs, TResult>`     | —     | the contract of the class                                                                                                   |
| `AbortableDelegateFunction<TArgs, TResult>` | —  | the type of the wrapped function: `(signal: AbortSignal, ...args: TArgs) => Promise<TResult>`                               |
| `AbortedException`                       | —     | rejection of a superseded or aborted call; also the `reason` of its signal                                                  |
| `isAbortedException(error)`              | —     | type guard, so callers can ignore the rejection of a superseded call in one line                                            |

The semantics, in short:

- A `call()` aborts the running call: its signal is aborted with the
  `AbortedException` as `reason`, and its promise rejects with that exception
  **immediately**, not when its function eventually settles.
- A function that ignores the signal still cannot win: when the function of a
  superseded call settles later, its result is discarded and its rejection is
  swallowed. A reader that cannot cancel its request is therefore safe to wrap.
- A cooperative function passes the signal to `fetch`, or checks
  `signal.aborted` (or calls `signal.throwIfAborted()`) after each `await` and
  skips its side effects.
- A rejection or a synchronous throw of the function rejects the call with that
  error; the delegate is reusable afterwards.
- A `call()` made from inside the function supersedes the outer call.
- There is no implicit debounce: compose with `DebouncedDelegate` for a quiet
  time.

```ts
import { AbortableDelegate, isAbortedException } from "@mantlebee/ts-core";

const search = new AbortableDelegate(async (signal, query: string) => {
  const response = await fetch(`/api/users?q=${query}`, { signal });
  const users: User[] = await response.json();
  if (!signal.aborted) render(users);
  return users;
});

search.call("t").catch((error) => {
  if (!isAbortedException(error)) throw error; // superseded: ignore
});
const users = await search.call("ts"); // the result of "ts"
```

A superseded call **rejects** rather than resolving with the result of the
call that replaced it: the caller awaited a result for *its* arguments and must
not take another's for it. `isAbortedException` keeps the `catch` to one line.

## 2. AsyncLock

When several independent delegates share one resource (three kinds of reads
writing the same filter of one data source), "the latest call wins" is the
wrong rule between them: each must complete, one after the other.

`AsyncLock` is an exclusive, non-reentrant, FIFO lock, in the new `locks/`
folder: `run(fn)` runs `fn` once every function enqueued before it has
settled. The lock is held for the duration of `fn` and released whatever its
outcome, so a failure does not block the next function. The folder is new
because a lock is shared by many callers, while `delegates/` wraps one
function.

| API                       | 1.2.1 | 1.3.0                                                                       |
| ------------------------- | ----- | --------------------------------------------------------------------------- |
| `AsyncLock`               | —     | exclusive, non-reentrant, FIFO lock                                         |
| `AsyncLock.run(fn)`       | —     | runs `fn` once every function enqueued before it has settled; resolves or rejects with its outcome |
| `AsyncLock.isLocked`      | —     | `true` while a function is running                                          |
| `AsyncLock.pendingCount`  | —     | number of functions waiting for the lock                                    |
| `IAsyncLock`              | —     | the contract of the class                                                   |

Reentrancy is a deadlock: a `run()` called from inside a running function
waits for that function, which waits for the inner `run()`. An async caller
has no identity, so it cannot be detected cheaply; it is a caller error.

Combined with `AbortableDelegate`, a function enqueued by a call that was
superseded while waiting for the lock checks its signal as soon as it starts
and returns at once:

```ts
import { AbortableDelegate, AsyncLock } from "@mantlebee/ts-core";

const lock = new AsyncLock();
const search = new AbortableDelegate(async (signal, query: string) =>
  lock.run(async () => {
    if (signal.aborted) return; // superseded while waiting
    applyQueryFilter(query);
    await dataSource.read();
    if (!signal.aborted) suggestions = dataSource.items;
  })
);
```

## 3. Checklist

1. Update the dependency: `npm install @mantlebee/ts-core@^1.3.0`.
2. Where a state must reflect the **latest** of overlapping async calls (a
   data source `read()`, a search as you type), wrap the function in an
   `AbortableDelegate` and ignore the rejection of superseded calls with
   `isAbortedException`.
3. Where several delegates write the **same** resource, run their functions
   under one `AsyncLock` and check the signal as the first thing inside.
